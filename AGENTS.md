# AGENTS.md — Ceasefire Line

Инструкции для кодовых агентов (Claude Code, Codex и др.). Источник истины по правилам игры — `docs/gdd.md`. Этот файл — про то, **как** писать код.

## Что это за проект

**Ceasefire Line** — гекс-варгейм уровня Strategic Command про локальные войны после 1945 года. Первый выпуск: Арабо-израильские войны 1967 и 1973 годов.

- Оперативный уровень, ходы IGOUGO, сценарии на вечер (4–20 ходов).
- Гекс 10 км (локальные театры — 5 км), ход 12 часов (день/ночь), юнит — бригада.
- Нет дипломатии, нет строительства, снабжение облегчённое (градиент 0–10), технологии — поколения по датам + ускорения за MPP.
- Платформы: стратегическая карта в браузере на десктопе; тактические бои в Telegram Mini App (этап 2). Обе — один клиент.
- Режимы на старте: против ИИ и хотсит. Онлайн — позже, поэтому ядро должно быть детерминированным с первого дня.

## Стек

| Слой | Технология |
| --- | --- |
| Ядро (правила, бой, снабжение, ИИ, сценарии) | Rust, без зависимостей от браузера и ОС |
| Мост в браузер | `wasm-bindgen`, сборка `wasm-pack --target web` |
| Клиент (карта, юниты, UI) | TypeScript + PixiJS + Vite; панели — HTML/CSS поверх канваса |
| Утилиты (симулятор боя, прогоны ИИ, импорт DEM/OSM) | Rust CLI на том же ядре |

**Не использовать:** Bevy и другие игровые движки, ECS-фреймворки в ядре, async в ядре.

## Команды

```bash
cargo fmt --all
cargo clippy --workspace --all-targets -- -D warnings
cargo test --workspace
wasm-pack build crates/wasm --target web --out-dir ../../client/src/wasm   # когда появится клиент
cargo run -p sim -- combat-matrix                                          # пример CLI
cargo run -p sim -- check-data                                             # загрузка data/*.json и всех сценариев
```

Перед тем как считать задачу выполненной: `fmt`, `clippy` без предупреждений и все тесты зелёные.

**Каждый коммит собирается сам по себе.** Данные и код, который их читает, — в одном коммите (новое поле в `rules.json` вместе с полем структуры). Проверки механические — git-хуки из `scripts/hooks`, один раз после клонирования:

```bash
scripts/install-hooks.sh      # git config core.hooksPath scripts/hooks
```

- **pre-commit:** `cargo fmt --all --check && cargo check --workspace && cargo run -p sim -- check-data`.
- **pre-push:** то же плюс `cargo test --workspace`.
- **CI** (`.github/workflows/ci.yml`) на каждый push и pull request: те же шаги плюс `clippy`.

Обходить хуки через `--no-verify` нельзя: если проверка не проходит, чинить до коммита. В цепочках команд проверка и коммит соединяются через `&&`, а не `;`. Опубликованную историю ради исправления не переписывать — чинить следующим коммитом и отметить это в `docs/decisions.md`.

## Архитектура ядра (обязательные принципы)

1. **Ядро чистое.** Никакого ввода-вывода, системного времени, глобального состояния, `thread_rng`. Данные приходят в ядро уже разобранными (serde из JSON делает вызывающий код или отдельный модуль загрузки).
2. **Команды и события.** Состояние меняется только через `GameState::apply(Command) -> Result<Vec<Event>, RuleError>`. `Command` и `Event` сериализуемы (serde). На этом строятся реплеи, ИИ, отмена хода и будущий онлайн.
3. **Детерминизм.** Свой сидируемый ГПСЧ в `core::rng` (например, ChaCha8 или PCG с фиксированным алгоритмом). Одинаковые состояние, сид и команды → одинаковый результат на native и в WASM. В формулах только базовые операции над `f64` (без `powf`, `exp`, `sin` и т. п. в игровой логике).
4. **Прогноз = разрешение.** Прогноз боя (R-COMBAT-03) и сам бой используют одну функцию расчёта параметров (`n`, `A`, `D`, `p`); прогноз возвращает мат. ожидание и 10/90-й перцентили биномиального распределения, бой — выборку.
5. **Data-driven.** Никаких магических чисел в коде: все числа из GDD живут в `data/*.json` или в параметрах сценария. Дальности в данных — в километрах; перевод в гексы при загрузке сценария (R-SCALE-01).
6. **Гексы.** Осевые координаты `(q, r)`, ориентация flat-top, соседи и расстояния — по [Red Blob Games](https://www.redblobgames.com/grids/hexagons/). Стоимость пути и снабжение — Dijkstra по стоимости AP.
7. **Округление.** `n = round_half_up(Strength × Readiness)`; вероятность `p` — `clamp(0.30 + 0.06·(A − D), 0.05, 0.90)`. Все спорные округления фиксируй в `docs/decisions.md`.

## Правила игры в коде

- Каждое правило GDD имеет ID (`R-COMBAT-02`, `R-SUP-02`, …). Функция, реализующая правило, помечается doc-комментарием с ID: `/// R-SUP-02: распространение снабжения`.
- Тесты называются по ID: `r_combat_02_tank_vs_infantry_1973`.
- **Примеры из GDD — обязательные тесты** (допуск ±0.01 для ожиданий):

| Правило | Вход | Ожидается |
| --- | --- | --- |
| R-UNIT-01 | снабжение 8, мораль 85%, опыт 1 | Readiness ≈ 80% (0,9 × 0,85 × 1,05) |
| R-COMBAT-02, 1967 | танки: Str 10, Rdy 90%, Exp 1, soft attack 5; пехота: Str 8, Rdy 80%, Entr 2, равнина, def 4, hard attack 2; танки def 5 | n = 9, A = 5,5, D = 5,2, p = 0,318, E[потери пехоты] = 2,86; ответ: n = 6, p = 0,09, E[потери танков] = 0,54 |
| R-COMBAT-02, 1973 | то же, у танков броня ур. 2 (def 6), у пехоты ПТУР ур. 2 (hard attack 2 + 4 = 6) | D танков = 6,6, p = 0,264, E[потери танков] = 1,58; соотношение 0,55 |
| R-SUP-02 | источник 8, 6 гексов по дороге + 2 по пустыне (5 AP) | Supply = 6; рядом со штабом (бонус +1) — 7 |
| R-MOVE-04 | танковая бригада 5 AP, 2 удара: 2 гекса по равнине, затем атака | после атаки 2 AP: доступно движение на 2 AP или вторая атака; после второй атаки 1 AP и движение запрещено; пехота после атаки — 0 AP |
| R-MOVE-06 | наземный юнит входит в пустой гекс противника; затем уходит | гекс сразу меняет владельца и остаётся за ним после ухода |
| R-AIR-03 | ЗРК: air attack 9, Str 8, Rdy 90%; самолёт: air def 5; доля выстрелов 0,3 | p = 0,54, выстрелов 2, E[потери] = 1,08; второй ЗРК стреляет с p × 0,8 → суммарно ≈ 1,94 |
| R-AIR-02 А | ударная ур. 2 (Str 10, Rdy 90%, soft 6) по пехоте (Str 8, Rdy 80%, AirDef 3, окопы 2); местность не учитывается | n = 9, D = 3,9, p = 0,426, E = 3,83; ответ n = 6, A = 1, D = 5, p = 0,06, E = 0,36 |
| R-AIR-02 Б | МиГ-21 ур. 1 (Str 8, Rdy 80%, air 6, def 5) против эскорта F-4 ур. 2 (Str 10, Rdy 90%, опыт 1, air 7, def 6) | эскорт p = 0,462, E[МиГ] = 4,16; МиГ p = 0,264, E[эскорт] = 1,58; ударная группа без потерь |
| R-AIR-02 В | тот же МиГ против ударной ур. 2 без эскорта (def 5, air 3) | p = 0,36, E[ударная] = 2,16; ответ p = 0,18, E[МиГ] = 1,62 |
| R-AIR-02 Г | ударная ур. 2 (soft 6) по аэродрому с МиГами | D = 2 (на земле), p = 0,54, E = 4,86; вся авиация в гексе −30% готовности |

- Если GDD противоречив, неполон или пример не сходится с формулой — **не выдумывай молча**. Выбери самое простое толкование, запиши его в `docs/decisions.md` (дата, ID правила, вопрос, принятое решение) и сообщи в итоге работы.

## Этапы (раздел 18 GDD)

1. **Ядро правил без графики** — закрыт. Гексы, юниты, движение и ZOC, бой, снабжение, MPP, загрузка данных, детерминизм, `sim combat-matrix`. Готово, когда все примеры из таблицы выше проходят как тесты.
2. **Редактор карт (минимальный)** — закрыт. Импорт DEM/OSM (`mapgen`), кисть местности, стороны гексов, владение, расстановка юнитов, запекание живописной карты в тайлы (`mapgen bake`); «Голаны-67» собраны на реальной карте.
3. **Вертикальный срез** — закрыт. «Голаны-67» в браузере, хотсит: все команды сценария в интерфейсе (HUD по утверждённому макету), панели R-UI-04, слои R-UI-02/03, удобство R-UI-05, без тумана войны; приёмка — `npm run e2e` (`client/e2e/fullgame.mjs`).
4. **ИИ v1 и «Синай-67»** ← текущий этап. Крейт `ai` (R-AI-01/02), режим «против ИИ», `sim` для прогонов ИИ против ИИ; авиация без зонтиков ПВО (R-AIR-01/02); сценарий «Синай-67» на реальной карте. Готово, когда пройдены проверки темпа и исхода из раздела 17. План — `docs/plans/stage-4.md`.
5. 1973: ПВО-зонтики, мосты, ночь, ускорения технологий, флот.
6. Полировка: туман войны, APP-6, реплеи, «Эскалация-73».
7. Этап 2 проекта: тактические бои в Telegram Mini App, онлайн.

Не забегай вперёд: не добавляй рендер, сеть или ИИ, пока текущий этап не закрыт.

## Стиль кода

- Rust 2021, stable. Идентификаторы, комментарии и сообщения коммитов — на английском; документация в `docs/` — на русском.
- Ошибки правил — типизированный `RuleError` (thiserror), без `panic!`/`unwrap()` в ядре вне тестов.
- Зависимости ядра — минимальные (`serde`, `serde_json`, `thiserror`, ГПСЧ). Новую зависимость обосновывай в описании изменений.
- Небольшие модули, чистые функции, тесты рядом с кодом (`#[cfg(test)]`) плюс интеграционные в `crates/core/tests/`.
- Коммиты: Conventional Commits с ID правил, например `feat(core): supply propagation (R-SUP-02)`.

## Содержание и тон

- Реальных имён командиров нет: штабы называются по соединениям («Штаб 3-й бронетанковой дивизии»).
- Ядерное оружие — только в сценариях с флагом `alternative_escalation` (R-NUC-01).
- Тексты интерфейса и событий — нейтральные по отношению к сторонам конфликта; строки UI — через файлы локализации (`ru` первым), не хардкодом.
